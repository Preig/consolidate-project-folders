# Conditional verification

Read only the relevant sections. A simple merge does not require a full rebuild or machine-wide search.

## Links, documents and bundles

Capture failures before moving. Check active HTML/CSS resources, literal/dynamic JavaScript routes as appropriate, meaningful fragment IDs, launchers, shortcuts, config paths and source/build generators. Server-root routes differ from filesystem-relative links. Templates can request temporary placeholders before hydration: check final bindings and retain diagnostics.

Inspect Windows shortcut target, arguments, working directory and icon without launching. Repair external shortcuts only within authorized relocation scope. Keep archived packages self-contained or document their restored-root assumptions.

For PPTX/OOXML relationship-only edits, keep rollback bytes and compare uncompressed parts. Change intended relationships, preserve fragments, validate targets/internal structure, and prove unchanged slide/note/media parts. Avoid re-saving a large deck through an authoring library solely to rewrite targets if targeted package edits preserve it better. Use appropriate document tooling/visual QA for content or layout changes.

Compare complete bundle relative-path/hash manifests, including required hidden/config/data/source files. A same-hash asset can be necessary in several bundles. Archive distinct builds intact rather than leave partial deduplicated shells.

## Data and runtime

Snapshot protected files before tests. Use copies or fresh data/profile/TEMP folders, owned ephemeral loopback ports and suppressed automatic browser launches. Disable live connectors; use fixtures/mocks instead of credentials or real messages/payments. Never reset/seed original databases for a demo.

Inspect SQLite through a read-only, transaction-consistent snapshot and run integrity/foreign-key checks where meaningful. Observe active writers/WAL/SHM. Do not use `immutable=1` on a live WAL database and call its main file a complete snapshot; use proper SQLite backup or quiescence. Preserve separate company/demo/backup states. Parse JSON/JSONL and inspect aggregate/schema facts without printing private records.

Separate presence, startup, workflow and full acceptance. Prefer bundled self-tests and meaningful source regressions. Use browser workflows where they test actual migration dependencies; complement assertions with screenshots. Track/stop only owned processes, confirm port closure and rehash protected scopes.

## Missing sources

Search named roots, known build paths, development mirrors, relevant Downloads/Desktop locations and archive indexes first. Expand broader local filename/content search when authorized/useful. Record excluded system/cache trees, access failures, unsupported archives and cloud/offline gaps. Avoid unrelated document contents; preserve synced mirrors and original external workspaces.

Recover app code, required assets/fixtures, tests, dependency manifests/locks, build/package recipes, icons, schema/migrations and compact provenance. Omit caches, environments, generated binaries, runtime secrets/databases and redundant source ZIPs matching retained editable trees. Keep required bundle-local source dependencies even if bytes exist elsewhere.

An EXE hash match identifies the same binary; a mismatch alone does not prove different source. Compare releases and actual app modules/resources when needed, using format-aware inspection or an available reverse-engineering workflow for binary claims. Matching code/resources does not prove a clean rebuild.

Restore missing historical revisions only from literal complete files or strictly matching patches. Preserve history references, sequence, hashes and independent checks. Do not label guessed decompilation original source. Keep differing interface revisions separate even when core engines match.

## Requested isolated rebuilds

Copy the selected source to a separate workspace. Preserve current EXEs/data and authoritative source. Record input hashes, exact commands, tool versions, freezes, output hashes and patches. Candidates belong in workspace/output folders; replacement/deployment is separate.

Prefer an isolated environment matching the recipe. Distinguish missing offline dependencies from source defects. A verified dependency copy can be used when permitted/documented: verify copied bytes/versions and dependency consistency, and mark fresh internet installation untested. Keep caches/TEMP local; avoid global installs and preserve user policy/approval controls. Finish dependency staging before starting a build.

Preserve generated absolute-path specs as provenance; regenerate or adapt paths in copied build material. Do not rerun historical bootstrap scripts that overwrite finalized sources.

Run source regressions, rebuilt self-tests and appropriate UI/workflow/agent-interface checks with synthetic data. Investigate real failures before editing code. Compare packager warnings with source usage, original provenance and actual tests: unchanged warnings do not prove optional branches work. Retain failed logs and distinguish corrected harness/environment errors from app defects.

Test delivered copies with fresh profiles/data and preferably no Python paths/credentials. Stop test processes and rehash protected files. Report source match, successful build, runtime coverage, warnings, dependency-resolution status, binary reproducibility and deployment separately.
